# meal-rotation
personal meal rotation app

## Read and cook recipes

The existing **Open recipe** action opens an internal full-page recipe view. Tap ingredients and instruction steps to fade/unfade them. Scheduled meals keep separate progress for each plan, weekday, recipe, and linked parent; **Reset Progress** affects only the displayed occurrence. Cycling a meal out clears its progress. Meal Groups previews allow temporary taps without changing a scheduled meal's saved progress.

Use the optional **Cooking instructions** and **Recipe notes** fields in the existing meal editor. Put one step on each line and use `## Heading` for instruction sections. Existing ingredients, times, and recipe URLs remain in the same editor. The viewer links to the original recipe near the bottom. Keep Screen Awake, in Recipe settings, defaults on and requests a screen wake lock where supported.

Supported structured website/RecipeSage responses and file imports retain available instructions, sections, notes, and times. Bulk file data is imported together; missing source details are checked in the background, with unfinished work retained across refreshes. Browser access restrictions can prevent extraction. Existing nonempty recipe content is preserved when enrichment fails or returns blank fields; manual editing and the original link remain available.

Photo imports also retain recognized Instructions and Notes sections when present. Review OCR text in the editor before saving; image quality can affect recognition.

Recipe content stays on existing meal records, and cooking progress is saved separately and included in version-2 backups. Older backups remain supported. Export backups regularly. Very large libraries can exceed browser storage limits; failed saves/imports preserve prior data rather than truncating recipes. Physical-device wake-lock behavior depends on browser permissions and power settings.

## Add a recipe to a meal group

Tap the group's **+** to create an Idea and immediately open the existing recipe editor. That group expands, its Ideas section opens, and In Rotation closes. The new row and name field are brought into view using the existing mobile/keyboard positioning. Other groups keep their expansion preferences. Creation is guarded against repeated taps while the new draft is open, and Save re-enables adding. Cancel or discarding the draft removes the new unsaved recipe without leaving an empty entry; existing saved recipes are unaffected.

`tests/add_recipe_ideas_browser.py` checks both apps at 320px/360px, collapsed bottom-of-page groups and long lists, focus/scrolling, keyboard-sized viewports, native disabled-control taps and detached-handler reentry, Save/Cancel/outside close, reload, and preservation of existing recipes, schedules, groceries, progress, scaling and unrelated section preferences.

## Make ahead, Skip This Week, and favorites

Use **Notes & Reminders → Make Ahead** in Edit Meal to add explicit preparation tasks with same-day, one-day, two-day, or custom lead times. Existing prep/marinate fields are unchanged; instructions are not scanned for reminders. Weekly Overview shows tasks on their actual due dates and keeps checked tasks visible. Tasks outside the displayed week appear separately with dates. Completion belongs to one dated scheduled occurrence, including its meal-plan tab and linked parent.

My Rotation shows **Today's To-Do** beneath Cycle Meals/Cycle Back, using the device's local date and all meal plans even when tabs are hidden. Recipe-card calendar icons are removed. Incomplete tasks come first; the eye reveals/hides completed tasks, hidden by default. When all due tasks are complete and hidden, **All done!** remains with the eye. With no tasks due today the entire section disappears. A local-midnight timeout and foreground/focus checks update this section without rerendering cards or resetting an editor draft.

**Settings → Display → Show Make Ahead Reminders** controls planning-view visibility globally (default on). It does not change definitions or occurrence completion; Make Ahead editing remains available when hidden. The optional `mealRotationMakeAheadDisplayV1` preference is included in existing complete backups. Older backups default to enabled reminders and hidden completed Today tasks.

**Skip This Week** in a scheduled meal's options replaces just its independent group slot without recording cooking, moving its queue position, or advancing the week. Other days/tabs and retained grocery quantities remain intact. Existing linked-recipe priority is respected. Undo restores the skipped occurrence, its reminder checks, cooking progress, scaling and groceries. A linked-only attachment or one-time meal without an assigned group cannot be skipped independently; the app explains this and leaves it unchanged. No alternative also leaves the meal unchanged.

Tap a recipe's **heart** in the viewer, My Rotation or Weekly Overview to toggle its favorite status. Meal Groups shows filled hearts only for favorited main entries and omits hearts on linked entries. Its existing meal-options popup provides an outlined/filled favorite toggle beside the heading, including for linked recipes, without closing the popup. The grouped Choose Meal dialog has a compact **Favorites only** filter. Favorites stay in their existing groups. Normal cycling and Skip use deterministic weighted credits, targeting two appearances for a favorite per one for each regular recipe, subject to existing eligibility, retained slots, duplicate avoidance and linked-priority rules. A pool of only two recipes alternates to avoid immediate repeats; with no favorites the existing rotation is unchanged. Display sorting/manual recipe ordering is unchanged.

Recipe tasks/favorites and plan-level occurrence checks/weighted credits use optional fields in existing saved records and complete backups. Older records/backups need no migration. Cycle Back restores weighted scheduling history while retaining later explicit task/favorite edits. No working-app data is reset or rewritten on update.

Focused isolated-browser tests: `make_ahead_reminders_browser.py`, `skip_this_week_browser.py`, `favorites_weighted_browser.py`, `prep_skip_favorites_integration_browser.py`, and `personal_recipe_icons_browser.py`. Tests cover both storage namespaces, narrow touch viewports, real calendar offsets, reminders before the week, duplicate occurrences, linked replacements, checked grocery contributions, Undo/Cycle Back, 200 weighted cycles, no-favorite parity, reloads and complete backups. Physical Android behavior still needs a device check.

## Needs Adjusting

Needs Adjusting is only a status and optional note. Marking, editing or removing it never moves recipes, changes their rotation order, replaces scheduled meals, or records cooking dates. Flagged recipes cycle normally. Moving between Ideas and In Rotation remains a separate arrow action and preserves the warning.

Unmarked recipes show a small, lightly outlined **Needs Adjusting** button below instructions and regular notes. It opens the existing optional-note editor with Save/Cancel. Marked recipes show a compact note immediately below the title, with an amber circled exclamation heading, the app's trash icon at the top right, and a pencil **Edit note** action beneath the note. The bottom marking action is absent. Regular Notes remain separate.

Warning icons beside recipe names in Meal Groups, My Rotation and Choose Meal/search open a compact read-only pop-up with the same heading, trash and pencil styling. The pop-up shows the recipe name and any saved note, with X reserved for dismissal. **Edit note** switches to the existing editor. Empty notes need no placeholder text. The dialog remains above the recipe viewer, and taps do not trigger recipe-row actions.

Every actual removal, including Edit Recipe trash/uncheck actions, uses **Remove Needs Adjusting?** with the message **This will remove the warning and its note. The recipe and its place in your rotation will not change.** Only the **✓ Confirm removal** icon authorizes clearing; the **X Cancel removal** icon preserves it. Edit Recipe retains its normal staged Save/Cancel behavior. Removal clears the warning and note without changing recipe membership, scheduling, order or other data.

The existing optional `needsTweaking`/`needsTweakingNote` fields and complete backup formats remain unchanged; older data needs no migration. Both app versions include the feature with separate storage and no new setting, screen, group or label. Tests cover exact schedule/recipe/grocery/progress/scaling/history preservation, flagged/unflagged cycling parity, read-only pop-ups, all removal paths, linked/manual occurrences, reload/backups, mobile full/split/landscape layout and editor rollback interaction.

## Import cleanup and related recipes

Structured imports share a conservative instruction cleanup pass: recognizable image-only entries, account prompts, website metadata, and related-recipe lists are removed from cooking instructions. Temperatures, timings, quantities, cooking headings, and uncertain text are retained. Related recipe references are kept for optional review, separately from active relationships.

After a file import, choose **Review related recipes**, or use the reference review link inside the recipe viewer. New links start unchecked; an already saved relationship remains checked. Exact source identifiers, URLs, or unique normalized titles can reuse an existing meal. Ambiguous matches require the existing Linked Meals picker. A missing recipe can be imported and linked only when a usable source provides recipe content; a failed import saves no partial changes or empty placeholders. Mentioned recipes do not enter the schedule unless you explicitly select a link, which then uses the app's existing linked-meal behavior.

To clean an existing recipe, open **Recipe settings → Review instruction cleanup / related recipes**. Compare the original, editable proposal, and removed content, then Save or Cancel. Opening recipes and restoring backups do not run this cleanup on saved instructions. Original URLs and other recipe details remain intact; import references and ordinary linked-meal IDs are included in existing backups. Sources that require login or block browser readers may need manual import.

## Refresh Recipes from RecipeSage

Open **Settings and backups → Data & Backups**, choose your RecipeSage JSON/JSON-LD or ZIP export, and tap **Refresh Recipes**. The existing importer extracts content. A brief refreshed/skipped count replaces the old repair preview, cleanup, URL retry and manual backup-verification workflow. The test app uses its own storage and safety-backup database; the retired one-time test cleanup no longer runs.

The refresh matches RecipeSage UUIDs or saved RecipeSage URLs first. A unique exact normalized name is a fallback only when saved source IDs do not conflict. Duplicate/ambiguous source entries and incomplete ingredients/instructions are skipped. Existing group copies sharing a source keep their individual IDs. No recipes, groups, links or scheduled slots are created or deleted.

Only ingredients, instructions and confidently imported notes are refreshed. Personal/uncertain notes are preserved; the existing conservative recognizer can remove proven legacy RecipeSage footer clutter. Notes matching the export verbatim, an empty field, or the previous refresh's recorded imported notes can receive fresh source notes. Missing source notes never erase existing notes. Existing recipe names, groups, manual order, rotation membership, dates, times, labels, URLs, links and other fields remain intact. Recipes whose changed content would invalidate saved ingredient associations or completed cooking tokens are skipped.

Before changing any recipe, the complete existing version-2 storage backup is validated, saved in IndexedDB, read back and checked, then automatically downloaded as `meal-rotation-before-recipesage-refresh-<timestamp>.json`. Keep that file; **Restore backup** restores the entire pre-refresh state. Backup failure stops the operation. All proposed content is validated before a single atomic primary-data write. Concurrent changes and failed writes leave recipe data unchanged. No normal refresh writes unrelated storage, cooking progress, settings or scheduling history.

`tests/recipesage_refresh_browser.py` tests both apps at a 360px mobile viewport, including ambiguity, personal notes, complete backup restoration, repeated refresh/reload, sandbox isolation, and injected backup/write/concurrency failures. Optional `--backup` and `--export` arguments run the same preservation checks against private supplied files without committing their contents. Existing importer extraction tests remain applicable.

## Meal Groups display order

Meal Groups retains its existing weekday/scheduled-group ordering until you rearrange it. Long-press a group name, header background or noninteractive card area for about 550 ms, then drag up/down. Normal swipes still scroll the page. Chevron, edit/add buttons and recipe controls keep their existing actions. Drag toward the screen edges to auto-scroll through long lists. All cards are visually collapsed only during the drag; their expanded states return on drop or cancellation. Holding without moving saves no order. Cancellation or a failed save restores the previous order. Existing edit-menu arrows can also move any group using the same display-only order, including weekday-assigned groups.

A successful rearrangement saves `mealRotationGroupDisplayOrderV1`, a list of group names used only by the Meal Groups page. It never changes the category array, weekday assignments, rotation, linked recipes, grocery selections, cooking progress or scaling. Weekday changes no longer move groups once a custom override exists. New/imported groups append in creation order; renames retain their position and deletions remove their entry. Unknown/stale names are ignored, and malformed stored order falls back to the normal layout without rewriting that storage during loading.

**Reset to Weekday Order** appears beneath the Meal Groups heading once a custom order exists. It clears the override and immediately restores the current automatic weekday/scheduled-group arrangement, without a confirmation dialog or assignment changes. Custom ordering/reset participates in existing undo history. Version-2 backups include the override through the existing app-storage snapshot; a backup without the key uses the default order, and restoring a legacy version-1 backup clears a local override. The isolated test app stores its order only inside its existing sandbox prefix.

## Updates and deployment

Publish the HTML files together with `pwa.js`, `service-worker.js`, both `.webmanifest` files, and `icons/`. Online launches check for current app files and fall back to the cached app when offline. A service-worker update waits for existing app windows to close; it does not force an editing session to reload. Close all regular/test app windows and reopen online to finish a pending update. Updates do not clear recipe storage.

When changing the offline shell, increment `SHELL_VERSION` in `service-worker.js`. Only this app's static files are cached; imports, backup files, and unrelated site resources are excluded. Old shell caches for this app's exact scope are cleaned up after the new worker activates.

For local development, serve the checkout with an HTTP server, such as `python3 -m http.server 8000`, and open it on localhost. Installation and service workers require HTTPS in production; opening an HTML file directly still runs the app without offline installation support.

## Recipe viewing modes

Inside a recipe, **Split View** puts ingredients above instructions with independent scrolling. Drag the center handle (or focus it and use arrow keys) to resize the sections; **Full View** returns to the single scrolling layout. The mode and divider position are saved locally and included in backups. Changing modes does not change occurrence-specific cooking progress. Imported instruction formatting is cleaned for display without rewriting older recipe records or their progress identifiers.

In **Recipe settings** (the viewer’s gear icon), **Sync Ingredients** is a checkbox that optionally follows the instruction near the upper-middle reading position after scrolling pauses. It starts off and remembers your preference. Relevant ingredients receive a blue-tinted background without changing cooking progress. Manually browsing ingredients pauses following; scrolling instructions again or switching sync off and on resumes it. Divider dragging and ingredient taps do not request synchronization, and reduced-motion preferences are respected.

Automatic matching is conservative and local: it recognizes explicit English ingredient names, plurals and preparation words, and clearly labeled ingredient sections such as Sauce or Marinade. It does not infer missing group membership or choose between ambiguous duplicate names. Unmatched instructions leave the ingredient position unchanged. In **Edit meal → Ingredient links for steps (optional)**, select a step and choose ingredients to override automatic matching; selecting Automatic clears the correction. An empty manual selection intentionally links no ingredients. Corrections save with the meal and its backups, independently of occurrence-specific cooking progress. Exact content matching preserves links across reordering; changed, removed, or identical duplicate items invalidate links rather than redirecting them.

With Sync Ingredients enabled in Split View, completing a step fades it immediately and advances to the next step after 350 ms. Manual scrolling, another interaction, closing the recipe, and changing modes cancel pending advancement. Undoing a step and completing the final step do not advance. Reduced-motion preferences are respected.

**Auto-complete Ingredients**, beneath Sync Ingredients in the same settings panel, is optional and starts off. Sync Ingredients is disabled outside Split View; automatic ingredient completion is disabled when synchronized Split View is off. Saved preferences are retained while unavailable. When enabled, subsequent instruction completions can fade confidently associated ingredients only after every associated step is complete. Explicit ingredient taps always win, including manually restoring an automatically completed ingredient. Turning the setting on or off does not retroactively change progress. Undoing a step reevaluates its automatic ingredient marks while preserving manual choices. Session metadata is optional and backward compatible with older backups; resets and rotation remove it for the affected occurrence. Meal Groups previews keep temporary progress separate from scheduled meals.

## Linked-recipe viewer tabs

The strip beneath the four viewer toolbar icons shows recipe names without a Main prefix. The initially opened recipe is the fixed anchor and has no individual close control, even after it moves. The entire strip is hidden when only that recipe is open. Linked recipes open or select another tab. Closing an active linked tab returns to the initial recipe; closing an inactive tab leaves the current recipe selected. The toolbar X closes the whole viewer. Recipe tabs match the rounded borders and selected styling of the Breakfast/Lunch/Dinner tabs. Full names display whenever they fit; when their combined widths overflow, labels abbreviate to the first word plus the next initial (for example, Crying T… and Puerto V…). Single-word labels use ordinary ellipsis when needed. Full names remain available as accessible labels and tooltips, and recipe headings stay unchanged. The strip scrolls horizontally, with keyboard arrow/Home/End navigation and 44-pixel touch targets. Long-press a tab name for 550 ms, then drag to reorder any tab; dragging near either edge scrolls through offscreen tabs. A short swipe scrolls the strip without reordering or selecting. Close buttons retain their separate tap targets. Drag cancellation restores the previous order. Reordering preserves active selection and each tab’s occurrence, progress, scaling, mode, divider and scroll positions. The order lasts for the current viewer session (including Edit Recipe return), and opening a tab appends it without rearranging the others. No linked-meal order or relationship is saved by this gesture.

**Automatically open linked recipes in tabs**, in main **Settings → Display**, defaults off and is included in the existing view preferences and backups. When enabled, only the main recipe's direct links open initially. Opening tabs does not change rotation membership. Each tab retains Full/Split mode, divider ratio, ingredient/instruction/full-view scroll positions, progress and scaling. Switching cancels pending guided advancement and pauses synchronization until an instruction interaction resumes it. Save or Cancel an ingredient-link draft before switching. Edit Recipe returns to the same tab deck; Reset Progress affects only the active occurrence and retains its scale.

Scheduled progress and scaling continue using the existing V1 keys and `[planId, day, mealId, parentId]` identity, never a title or recipe ID alone. Linked tabs resolve only within their source occurrence's plan and day: an exact linked-parent occurrence takes precedence, followed by a unique independently scheduled instance. Another parent's occurrence, an ambiguous match, or an unscheduled source is never borrowed. Unresolved links show a temporary-progress notice and retain their progress, manual overrides and scaling in the current viewer's cache, scoped to their source occurrence. Closing and reopening a linked tab restores that state; closing the whole viewer ends temporary sessions. Different main-meal viewer sessions cannot share temporary progress. No scheduled-state migration or replacement storage is introduced, and existing backups remain compatible.

Recipe content and ingredient-to-step associations remain on the shared recipe record. Existing reconciliation retains compatible occurrence progress when content changes, without marking newly added items complete. Cycling an occurrence clears only that occurrence and its associated linked progress/scaling; other days remain independent. Grocery totals still read each scheduled occurrence's multiplier.

## Android touch handling and split divider

The entire recipe-tab strip (including tab padding, gaps and close buttons) uses one non-passive touch stream. Touch starts prevent browser takeover; a short stationary touch performs exactly one selection/close, a swipe scrolls without clicking, and a 550 ms hold starts reordering with edge scrolling. Mouse/pen use separate pointer handlers. Android pointer cancellation/capture-loss events do not cancel an ongoing touch stream; actual touch cancellation or a second finger cancels the reorder. Sorting uses CSS order while a finger is down, and commits DOM order after release, so the held element is never detached during a drag. The fixed main anchor, session-only order and independent cooking progress remain unchanged.

The split divider draws a 10px band and 3px grip inside a transparent 44px target. The target occupies its own layout space, so it does not overlay ingredient or instruction controls. Touch, mouse/pen and existing keyboard resizing preserve the per-tab split ratio using the same preference storage; vertical scrolling in each pane remains independent. Full View hides the divider. Physical-device behavior still depends on browser/OS versions; regression tests use Android-sized Chromium touch simulation, including capture-loss/pointer-cancellation event variants.

## Cycle Meals with linked recipes

A weekday group explicitly assigned in the selected meal plan owns a selectable Cycle Meals slot, even when a linked recipe currently fills it. For example, Tuesday Rice and Sides show separate choices for Thai Garlic Pork and its linked rice. A linked recipe whose group is not assigned that day remains an attachment: it has no checkbox and follows its parent. Selection uses the plan/day/group slot and existing parent occurrence identity, not names or recipe ID alone.

Unchecked choices explicitly retain their displayed recipe and take priority over an incoming linked replacement. This retention is scoped to the selected plan and slots; a same-day group in another plan is not newly locked by that choice. Rotating only a side keeps the main and selects a new side without immediately reinstating the main's old link. Rotating both permits the replacement main's linked side to take priority over the group's normal queue choice. Existing linked replacement rules also apply when a group was not explicitly retained. This changes the scheduled display without editing the main recipe's saved `linkedMealIds` or weekday assignments.

An optional `cycleSlotChoices` map on the existing plan records the chosen recipe, its original parent context, explicit retention and retained-parent overrides. The existing `cycleRetainedSlots` map keeps frozen occurrences stable against duplicate avoidance. Only cycling/Cycle Back writes these fields; existing records need no migration. Retaining a side across a main change keeps its original occurrence identity, completed steps and scaling. Other days and plans remain independent, including repeated recipes. Grocery totals continue to use the displayed occurrences and their scaling. The optional cooked-date action applies to selected slots and their true attachments.

The existing `mealRotationLastRotationBeforeV1` snapshot captures displayed occurrences, group-slot status and parent IDs. Full Cycle Back and Undo restore the snapshot as before. Partial Cycle Back preserves unselected slots and later recipe edits while restoring selected recipes and their original contexts. Older snapshots without group-slot status are classified from their saved weekday assignments, using the same scheduling/link/filter logic. Backups retain the optional plan/history fields; recipe content, IDs, links and settings keep their existing formats.

It then resolves linked replacements with the existing planner and chooses unused eligible recipes for ordinary selected slots that conflict with retained meals, linked replacements or other new selections. Linked priority, explicit retention and recipe-label filters remain in effect. When no unused eligible recipe is available, the slot keeps a repeat. Candidate attempts are bounded per slot, including conflicting linked definitions.

Only outgoing meals move to the queue's bottom or receive optional cooked dates. Skipped candidates keep their queue positions and recipe history. Choices use the existing per-plan overrides, cycle pins and link-context fields; there is no storage migration or automatic rewrite of existing schedules. Other tabs remain pinned unless explicitly included in the rotation. Existing Cycle Back snapshots and backup formats are unchanged.
